# Incremental state design

The caller prepares a versioned snapshot of module fingerprints, reverse module dependencies, analyzed results, and stored warnings. A new run compares its input profile and module fingerprints with that snapshot, computes an analysis plan, runs the affected modules, and atomically replaces the output snapshot. Reading one path and writing another must preserve the input snapshot.

Two designs were considered. Serializing the entire Engine would retain node and function IDs tied to one Core arena, and would mix warning selection with cached semantic results. A module-indexed snapshot instead uses qualified names and keeps reverse dependency repair, stored diagnostics, and display selection explicit. The module-indexed design follows native IPLT ownership and allows removed modules to be cleaned without analyzing unrelated modules.

The first verifiable unit is the pure invalidation plan. Its inputs are changed and removed module names, the previous reverse dependency graph, and current module membership. It expands dependencies transitively, removes only explicitly removed modules from the analysis set, clears all expanded modules from persisted results, and strips changed/removed modules from dependency values. This last detail follows `dialyzer_callgraph:strip_module_deps/2`; dropping graph keys or stripping the entire expanded set would change native behavior.

The native reference is OTP 28.3 `dialyzer_incremental:expand_dependent_modules/4`, called from an isolated copy of the installed module with its original private functions exported. This pass consumes no inference output. Subsequent units cover profile/version and warning-set invalidation, snapshot commit/reload, warning-map merging, and original operational test sequences. Passing dependency expansion alone does not verify persistent state or incremental analysis.

Source flow: `dialyzer_iplt:check_incremental_plt/3` compares version, implementation fingerprints, legal warning sets and module fingerprints. `dialyzer_incremental:start_report_modules_changed_and_analyzed/1` chooses full rebuild, reuse, safe removal, or partial analysis. Warning-module selection is applied when returning stored warnings; changing legal warning tags requires full analysis. New dependencies merge with the repaired old graph when writing the IPLT.

The parsed snapshot header now selects the native check result from analysis version, implementation digests, module digests, legal warnings and warning availability. Native version checking verifies the stored implementation entries against current fingerprints; an empty stored implementation list passes that test. Legal-warning mismatch takes precedence over module changes after version validation. These decisions pass 7,307 source-driven comparisons. Compiler hash extraction, corrupt-file errors and actual snapshot persistence remain separate open boundaries.

Warning merging retains the old map on uncollected warnings. Otherwise each new module list is built by prepending collected warnings, then unknown warnings; stored module entries take precedence over new entries. Reanalysis must discard old entries before this merge. Requested module order and duplicate requests remain observable. When selecting all modules, only membership is stable because native map iteration order is unspecified; final diagnostic sorting and deduplication determine the returned warning order. Warning/dependency merging and selection pass 7,460 native comparisons.

The shared finite ETF reader now preserves native classic and incremental record shapes in flat arenas. Field handles keep those arenas alive and decode compressed inner values only on demand. The boundary accepts legacy uncompressed incremental data; it does not eagerly validate unrelated fields. Rust-written copies of the real classic base PLT and a native-written IPLT reload into identical native info, type, contract, callback and exported-type tables. All 824 file gate outcomes pass, including missing, directory, malformed and shape cases. Runtime identity terms remain an explicit unsupported boundary.

Writes prepare and sync an exclusive temporary file in the destination directory, then rename and sync that directory. Existing symlinks resolve to their target; existing file write permissions and mode are preserved. Concurrent-reader tests observe only complete old or new snapshots during repeated writes. Distinct input/output transport checks verify unchanged input hashes. This proves transport and commit mechanics; production inference results, dependency/warning repair and fingerprint policy still need to enter one complete analysis lifecycle.

Compiler fingerprints use native stable abstract forms: only top-level file attributes lose the directory prefix. The shared Rust ETF encoder and MD5 implementation reproduce actual native BEAM fingerprints for all 327 compiler groups and 571 modules, plus 32 compiled map-attribute modules across the small-map/HAMT boundary. The compiler transport retains native `maps:to_list` order for fingerprint serialization and a separate validated `maps:iterator` permutation for pattern refolding. Captured inference outputs do not participate in this computation.
