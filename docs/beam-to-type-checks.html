01

Start with compiled BEAM files

For Elixir or Erlang, compilation happens first. The analyzer needs the program's debug information, not a disassembly of its virtual-machine instructions.

What enters the pipeline

The cache builder takes a list of BEAM paths. Each file represents a compiled module. Elixir macros have already expanded, so the analyzer sees the code they generated.

beam_lib.chunks reads debug_info and abstract forms. The debug-info backend compiles the module to Core Erlang with the Dialyzer compiler options. dialyzer_clean_core.clean then applies the same cleaning step used by the native analyzer.

A BEAM without the required debug information fails at this boundary. The current bridge does not reconstruct missing source information from bytecode.

Cache the compiler work

The cache key is SHA-256 of the BEAM bytes. A separate directory identifies the OTP, Elixir and compiler profile. The same bytes under the same profile can reuse their Core record.

Each entry has an ETF file and an atom sidecar. Temporary-file renames keep individual cache files whole. The manifest lists module files in input order and carries the compiler context, runtime atom layout and closure profiles.

Modules compile concurrently. Rust also reads and decodes module files concurrently, then restores their input order.

02

Turn Core into an analysis world

Core is a smaller language with explicit functions, calls, bindings, branches and exception paths. It gives both source languages one analysis representation.

%% A teaching example in Erlang
inc(X) when is_integer(X) -> X + 1.
bad() -> inc(hello).

%% Schematic Core shape, not an export
fun(X) ->
  case X of
    N when is_integer(N) -> add(N, 1)
    _ -> match_fail
  end

Core annotations retain origins such as source files and positions. Rust decodes flat node and term tables, builds stable labels, and indexes named and nested functions. A folded view helps pattern handling while the original view keeps the compiler's labels and structure.

Several inputs meet here

Program records function identities. DataflowNodes joins Core, labels and literal types. Closure analysis determines possible local call targets and escaping functions.

Prepared definitions include records, user types, candidate specs and callbacks. Imported PLT summaries provide facts about dependencies that are outside the current target analysis. PLT means Persistent Lookup Table.

The prior-store lifecycle matters. Explicitly purged modules are removed first. Graph cleanup uses prior membership, then current named keys are deleted before fresh inference. This prevents old target signatures from silently seeding a cold analysis.

Runtime atom and closure metadata preserve ordering and identity needed for OTP parity. They are compiler/runtime facts, not solved type facts.

Source facts

Core trees, annotations, exports, types, records, specs and callbacks.

Dependency facts

Imported signatures and contracts, BIF rules and closure call targets.

Fresh target state

Empty target signature table and candidate contracts. Missing previous signatures project as any arguments and result for the phase request.

03

Solve callees before their callers

A caller needs its callee's signature. Recursion makes that dependency circular, so the graph groups mutually recursive functions into one job.

The graph algorithm

The source graph code uses a two-pass, Kosaraju-style SCC algorithm. A depth-first traversal records reverse postorder over outgoing edges. A second traversal follows incoming edges in that order to collect strongly connected components, or SCCs.

Collapsing each SCC gives a directed acyclic graph. The scheduler uses a callees-first order. In the ordinary graph algorithm, SCC discovery takes O(V + E) traversal work; ordered tables and native-order compatibility add implementation costs.

Scheduling and cleanup

Graph cleanup distinguishes target functions, external calls and missing exported calls. External summaries remain available through the library store.

The parallel path starts an SCC after the required callee results commit. Independent SCCs can run together. Its visibility rules preserve the state each job would see in dependency waves. When types change, reverse reachability identifies callers that may need another pass.

04

A type is a set of possible values

The analyzer interprets code using abstract values. Instead of executing X + 1 for each possible X, it computes what argument and result types can succeed.

The type algebra

any admits every value. none is the empty type. More precise types retain atom sets, integer sets or ranges, tuple alternatives, list shape, bitstrings, functions, maps and nominal identities.

Intersection keeps values allowed by both facts. Union joins alternatives. Subtyping asks whether every value in one type belongs to another. Canonical constructors keep equivalent type shapes consistent.

unit is a separate special no-return type used by the solver. Recursive solving can retry with a unit return after a none result stabilizes. Treating unit and none as interchangeable would change the analysis.

05

Translate function bodies into constraints

Each SCC gets a constraint graph. Solving it finds compatible types for expressions, parameters, returns and recursive references.

Four node shapes

Atomic constraints relate type variables and type expressions. A conjunction requires all its children to succeed. A disjunction represents alternatives such as branches. A reference connects the current problem to another function's constraints.

Generation handles Core control flow, patterns, calls, BIFs, maps, captures and exceptions. Derived operations compute types from other bindings rather than storing only constant type facts.

For inc/1, the integer guard restricts the successful argument path. Addition then contributes argument and result facts. The actual generated graph contains more detail than this teaching shorthand:

T_X   ⊆ integer()      // successful guard
T_1   = 1
T_ret = add(T_X, T_1)  // derived result
T_inc = fun(T_X) → T_ret
Inside the solver
  1. Normalize the graph and prepare dependency information.
  2. Evaluate constraints against a binding map. Narrow bindings where required; discard failed alternatives.
  3. Use each changed variable's dependency mask to mark the children that read it.
  4. Reuse cached local bindings for untouched subgraphs. Reevaluate affected children.
  5. Join successful disjunction branches using the canonical type algebra.
  6. For recursive references, repeat with updated approximations until the relevant bindings stabilize.

A dependency mask maps a variable to child positions. This is the reason a local type update need not trigger a full tree walk.

There is also a loop inside a recursive SCC

seed recursive approximations from previous bindings ↓ solve the functions currently affected ↓ compare recursive bindings at bounded depth ↓ changed? → enqueue users of the changed variables → repeat stable? → retry none-return recursion with unit once if needed ↓ return the SCC's inferred bindings

SCC solving uses depth-four approximations. The outer phase projects the owned function results and validates candidate specs against them. Newly valid contracts become active for later phases. Contract activation itself counts as a change, even when the inferred signature stays equal.

06

Follow actual flows, then repeat

Constraint inference and module dataflow answer related questions. Alternating them propagates information through local calls, closures and recursive dependencies.

The module worklist

FunctionState stores arguments, returns, environments and callers. A FIFO worklist selects the next function. The body interpreter binds its parameters and evaluates Core with type maps.

Local calls forward argument types. New argument information schedules the callee. A changed return schedules its callers. Escaping functions need treatment that allows calls from outside the analyzed local context.

Case clauses narrow patterns and guards in scoped maps. Safe underapproximation can remove values covered by earlier clauses. Successful branches contribute to the joined result; failed branches do not.

Exactly when is it stable?

The SCC comparison checks equality after limiting function types to depth four. The module comparison instead checks whether the old limited type is a subtype of the new limited type. Failed or uncalled signatures do not trigger these comparisons.

Published signatures are limited to depth five. Bounding structural depth prevents recursive shapes from growing without bound. This deliberately trades precision for a finite representation.

Changed module labels select the next affected SCCs. The analyzer exits when the appropriate phase reports no further changes. It does not use a fixed number of whole-program passes.

07

Run the warning pass on stable types

Warnings come after inference converges. Intermediate uncertainty should not become a final diagnosis.

What gets checked

The diagnostic phase checks invalid or missing-function contracts, body calls and control flow, unused functions, no-return functions and callback conformance. Unknown calls and types, and missing exported calls, also arrive from declaration preparation and graph cleanup.

A call combines several distinct facts: raw success signatures, active contract domains, BIF domains and current local returns. Multiple possible call targets need alternative handling and warning consensus. Opacity checks preserve module-sensitive type identity.

Specs are candidates until SCC validation activates them. Invalid-contract diagnostics use converged signatures. This keeps a bad spec from becoming an unquestioned starting assumption.

How a warning becomes public

Core annotations and original declaration forms provide source origins and contract text. Contract-range warnings undergo origin rewriting and same-origin filtering.

Publication applies the requested warning profile and per-function or module suppressions. It combines retained analysis warnings with cleanup and unknown-reference warnings, orders and deduplicates them through the warning processor, and projects line or column locations.

Module diagnostics can run concurrently, alongside contract diagnostics. The collector restores module result order before public warning processing.

Illustrative finding

bad() calls inc('hello')

The argument 'hello' has no overlap with the successful argument type integer(). The diagnostic pass can report the failing call and no-return consequences. The real output carries warning terms and exact source locations rather than this teaching text.

Warning-pass signatures enter a separate documentation table. They do not replace the converged inference state. With report_modules, inference still covers the whole input world while module diagnostics and emitted probe signatures are restricted to the selected modules.

08

What leaves the pipeline

Finishing means the analysis has converged and the requested diagnostics have been published. It does not mean every possible runtime failure has been disproved.

Two modes, one inference loop

SuccessTypings performs inference and diagnostics. PltBuild returns the inferred state before the diagnostic phase, with no documentation table or raw analysis warnings.

The cache executable prints JSON containing status, module count, load and analysis timings, warnings and signatures. The underlying compiled entry owns richer state, including prepared definitions, the prior store and module dependencies.

Three different kinds of reuse

The Core cache skips compiler lowering for unchanged BEAMs. Imported PLT summaries supply external type facts. Solver caches and worklists avoid repeated work within an analysis.

These are separate mechanisms. Reusing a Core file does not skip target type inference. The cache executable does not itself write a complete updated native PLT. Classic and incremental persistence have separate code and acceptance work.

Why can a program with no warnings still fail at runtime?

Success typing computes approximations of successful behavior. Unions, depth limits and loss of correlations can hide errors. A warning profile can also suppress findings. This tool is not a proof that every execution succeeds.

Why do we need both constraints and dataflow?

The constraint phase solves relationships within function groups, including recursion. Dataflow follows argument forwarding, local return changes, environments, patterns and guards through modules. Each phase can provide facts the other needs on the next pass.

What establishes compatibility with OTP?

Differential checks compare compiler representation, type operations, generated constraints, inferred signatures and complete public diagnostics. Component agreement establishes that component's scope. Full acceptance requires fresh integrated runs with the relevant options and persistence lifecycle; historical counts are not a guarantee for the current checkout.

Where should I begin reading the code?

Start at compiled_analysis.rs for composition. Read core_analysis.rs for the outer loop, constraints/tree.rs for constraint solving, and body_flow.rs for dataflow. Finish with warning_publication.rs.
