# Native runtime context

Two modes keep correctness claims separate.

1. **Import a compiler oracle context.** `RuntimeContext::import` validates the captured version, atom layout and original closure profiles. It preserves the supplied atom namespace. This is useful for a differential run that must retain the compiler process's transient atom identities. Import does not infer how the namespace was originally created.
2. **Build a deterministic native context.** `RuntimeContext::native` reads the original Dialyzer BEAMs and allocates atom identities in a fresh `native-atoms-v1:<sha256>` namespace. It invokes no VM, NIF, compiler or subprocess. Names are sorted, assigned consecutive positive indexes and encoded with the existing OTP64 tagged-atom representation `(index << 6) | 11`. The existing native OTP hash and map traversal algorithms consume these identities.

The native constructor expects the complete workload atom set before analysis. The pipeline walks reachable source-form and cleaned-Core roots to collect atom names without retaining unreachable lowering placeholders in the namespace. The separate `module_atoms` helper collects literal atom names, module names and external-fun module/function names from typed Core modules. The builder also includes the six analyzer atoms used by the existing context exporter and original Dialyzer closure names. Atom allocation does not change halfway through a run. Its scope digest frames every UTF8 name by its length, so duplicate names and caller input order cannot change a scope. Changing the atom set changes the scope. Data built under different scopes must not be mixed.

Compiler-process atom indexes are transient VM state. They are not recoverable from a BEAM's atom table: that table has module-local indexes. Consequently this native namespace is not represented as a recovered VM namespace. Atom-dependent small-map and HAMT iteration can differ from a captured compiler process. All tables must be rebuilt under the native namespace. Exact compiler-oracle ordering is supported by imported contexts. Whole-system checks now compile every BEAM through the native lowerer and adapter, then compare complete warning JSON and all inferred signatures with the compiler baseline: 325 warnings and 31,050 signatures for Phoenix, 215 warnings and 39,126 signatures for Elixir. Both imported and fresh native contexts pass. Native runs use `PATH=/usr/bin:/bin`, which excludes the installed Elixir command. Separate strict compiler comparisons pass for complete forms, raw Core and cleaned Core on all 1,032 distinct inputs. Closure environment ordering uses original `FunT` profiles and does not invent closure code identities.

## Profile authentication

Native mode implements Elixir 1.19.4, OTP 28.3 / ERTS 16.2, Dialyzer 5.4, with the existing compiler options. It checks the complete original bytes of `dialyzer_typesig.beam` and `dialyzer_contracts.beam` against the pinned source installation SHA256 digests. It refuses other builds, including another build with nominally equal version strings. Updating the compiler profile requires an explicit source/profile migration and refreshed oracle evidence.

`fun_profile` reads the validated shared BEAM chunk parser, selects exactly one `AtU8` or legacy `Atom` table, validates atom count and string lengths, and decodes every 24-byte `FunT` row. Each row retains its original label, old index, captures and uniq; `new_index` is its table position, as in `CoreCache.fun_profile/1`. One-based atom references must point into the local table, captures cannot exceed compiled arity and closure names must be unique. Original-byte SHA256 is computed in Rust. The parser does not depend on debug info and does not load executable code.

## Evidence

The two original Dialyzer BEAM fixtures and captured `:beam_lib`/`:crypto.hash` profile JSON are under `tests/fixtures/beam_core_port/runtime_context/`. Tests compare every row and digest to the independent OTP oracle, exercise SHA256 standard vectors including a two-block padding case, reject malformed FunT references and modified compiler binaries, and verify deterministic hash namespaces and flat/HAMT traversal across reversed inputs.

The fixture binaries originate from the installed OTP 28.3 distribution, covered by the OTP Apache 2.0 license already identified by this port's notice. The JSON was captured with the same `:beam_lib.all_chunks`, `:beam_lib.chunks(:atoms)` and 32-bit row decoding used by `prototypes/core_cache/core_cache.exs`; no native reader generated the expectations. Production has no dependence on these test JSON files.

## Whole-workload scope review

For the fresh compiler baseline cache of the saved Phoenix and Elixir workloads, an independent ETF inspection covered all 1,032 distinct module files. It found 17,073 map occurrences and no external-fun values anywhere in the captured source forms, Core and transport metadata. Consequently the existing explicit `MissingExternalFunIdentity` hashing boundary does not block these inputs. This result concerns these exact baseline inputs; it does not add support for arbitrary external-fun map keys.

The analyzer's runtime hash consumers use module/function atom names already present in source forms and Core, declaration keys copied from those forms, and the existing fixed analyzer atoms. BIF-produced type atoms are values, not new runtime hash keys on these paths. No additional system atom was justified by the reviewed code. Digraph and SCC ordering is rebuilt under the fresh native namespace, which can change iteration order and the sequence of widening operations compared with the captured compiler layout. Whole-run signatures and warnings must be compared; equal hash support alone does not establish semantic parity.

The cold prior library used by these benchmarks has empty callback groups and type tables. A general nonempty prior library has a wider boundary: PLT persistence rehashes prior callback module names (`plt_tables.rs`), so the caller must include prior atom names before constructing its native scope. Imported callback/type artifacts also preserve their captured ordering provenance. This builder does not silently relabel those tables as native tables or rebuild them. Arbitrary prior-library migration requires its own evidence; the cold benchmark avoids that unresolved migration.
